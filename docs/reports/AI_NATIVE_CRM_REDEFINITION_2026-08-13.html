00 · Supersession decision

“CRM이 아니라 관제탑”을
이제 명시적으로 대체한다.

기존 DESIGN.md와 design context의 문구는 일반 CRM과 다른 감독 경험을 강조하기 위한 것이었다. 최신 사용자 의도는 여러 CRM의 장점을 모아 사람과 AI 직원이 회사 업무를 함께 처리하는 최종 CRM을 만드는 것이다.

01 · Executive decision

문제는 기능 부족보다
제품 문법의 분열이다.

현재 시스템은 전부 선형이지 않다. PoC와 작업은 독립 생성이 가능하다. 하지만 프로젝트는 딜 전환에 잠겨 있고, 지원은 API만 있으며, 리뉴얼은 위험한 투영 구현과 operator 경로만 있다. recurring production schedule은 증명되지 않았다. AI는 이 차이를 숨기지 못하고 내부 DB 구조를 사용자에게 떠넘긴다.

Customer context-centered · Work-driven · Gate-governed · Pipeline-observable
1

Context is home

고객과 지금 진행 중인 모든 일을 한 맥락에서 다시 시작한다.

2

Work is execution

딜·PoC·프로젝트·지원·리뉴얼은 각자의 typed lifecycle을 가진다.

3

Pipeline is a lens

영업 예측·자격검증·병목 분석을 지키되 다른 업무의 부모가 되지 않는다.

이 객체들은 따로 놓인 목록이 아니다. 각 업무가 작은 내부 그래프를 가지고, 고객 맥락에서 서로 연결되며, 결과와 사람 수정이 다시 다음 관찰·제안으로 돌아가는 하나의 순환 운영 그래프를 이룬다.

02 · Product invariants

다섯 가지 제품 원칙

01

고객은 척추다

연락처뿐 아니라 딜, PoC, 구축, 자산, 지원, 리뉴얼, 재무, 승인, AI 제안을 함께 본다.

02

일은 사실에서 시작한다

지원은 장애에서, 리뉴얼은 만료에서, 프로젝트는 계약·이행에서 바로 태어난다.

03

프로세스는 가드레일이다

업무 생성은 열고 돈·외부 약속·납품·삭제 같은 위험 행동을 증거와 승인으로 막는다.

04

AI는 계약을 가진 직원이다

권한, caseRef, 제안, 위험도, 승인, 실행, 감사, 학습이 한 루프에 있어야 한다.

05

유연함은 무규칙이 아니다

typed domain object와 hard edge를 지키고 사용자 정의 그래프·임의 상태는 첫 버전에서 배제한다.

03 · Current architecture

버릴 시스템이 아니라
재배치할 시스템이다.

고객·딜·PoC·작업·자산·지원·리뉴얼·견적·재무·승인·감사 모델은 이미 있다. 가장 비싼 자산은 부족하지 않다. 생성 경로와 화면 위계, AI 연결이 어긋나 있다.

Engagement와 StageEvent를 이렇게 잠근다

Engagement 관계

현재 opportunityId는 필수·unique다. 목표는 nullable + 한 딜 여러 구축 phase다. nullable read → deliveryKey/idempotency → formal migration → finance/RLS/convert 검증 순서로 바꾼다.

StageEvent 역할

영업 단계 이력과 예측 보정 신호로 유지한다. 사람 승인·AI 수정의 정본은 GovernedProposal, ApprovalRequest, DomainDecisionLog, DomainMemory다.

Action Proposal은 새 SoT가 아니다

제안 정본은 GovernedProposal, 사람 확인과 exact revision lock은 ApprovalRequest, 실행·학습 보조 기록은 DomainDecisionLog다. 승인한 canonical payload hash와 실행 payload가 다르면 transaction을 중단한다. best-effort DecisionLog는 실행을 허용하는 근거가 될 수 없다.

04 · Five journeys

사용자는 다섯 개의 다른
시스템을 배우고 있다.

숫자는 사용자 실험 결과가 아니라 생성 경로·화면 전환·숨은 전제조건· UI/API 불일치를 바탕으로 한 연구자 휴리스틱 심각도다.

7.5

신규 영업

생성은 쉽지만 BANT가 다른 탭에 있고, 6개 작업 단계와 7개 DB 단계가 겹친다. 등록 gate는 합리적이지만 AI rail은 실제 writer와 연결되지 않는다.

9.0

독립 구축 프로젝트

독립 Engagement 생성 버튼과 POST 경로가 없다. Opportunity conversion 경로는 있으며, 특정 딜 단계와 PoC를 만족해야 한다. 딜 자료 흡수에는 좋은 규칙이지만 프로젝트의 유일한 탄생 규칙으로는 틀렸다.

5.5

PoC

독립 생성은 이미 된다. 문제는 메뉴가 깊고, 딜 문맥 prefill과 link-back이 약한 것이다. 좋은 모델이 제품 연결에서 손실된다.

8.0

기술지원

자산·담당·SLA gate는 타당하다. 그러나 생성 화면이 없고, canonical service의 3상태 전이와 legacy 문자열을 투영한 UI 5컬럼이 다르다.

8.5

리뉴얼

수동 접수가 없고 투영 배치 구현은 임의 금액·임의 딜·대체 ID를 사용한다. privileged operator 경로는 있으나 recurring production schedule은 증명되지 않았다. 생성 필드와 화면 조회 필드도 달라 투영된 건이 보이지 않을 수 있다.

08.2 · Governed self-improvement

학습 로그가 아니라
검증된 반환 간선을 만든다.

결과를 저장하는 것만으로는 자가개선이 아니다. 실행 결과와 사람 수정이 개선 후보가 되고, 평가·사람 승인·버전 고정·점진 적용·감시·롤백을 거친 뒤 다음 관찰과 제안에 실제로 적용되어야 폐쇄 루프다.

Operate관찰 → 제안 → 승인 → 실행
Collect결과 · 사람 수정 · 운영 지표
Evaluate고정 평가셋 · 회귀 · 보안 검증
Govern사람 승인 · version · canonical hash
Roll outshadow/canary · 감시 · 승격/롤백
승격된 memory · prompt · policy version → 다음 관찰과 제안에 적용

직접 자기수정 금지

운영 AI가 prompt·policy·권한·writer를 직접 바꾸지 않는다. 로그는 개선 후보의 근거일 뿐이다.

버전 추적

모든 실행은 사용한 model·prompt·policy·memory·action registry version을 감사 기록에 남긴다.

실패 시 복원

수정률·오연결·권한·금액 오류가 임계값을 넘으면 이전 version 포인터로 즉시 되돌린다.

자가개선 = 기억 축적이 아니라, 평가되고 승인되고 되돌릴 수 있는 새 version이 다음 행동을 더 낫게 만드는 것.

데이터·그래프 경계의 진실 복구

리뉴얼 날짜·금액·대체 ID를 고치고 기존 FK·attachment·event를 node/edge registry로 목록화한다. 모든 AI 실행 version도 기록한다.

Phase 1

독립 업무와 로컬 서브그래프

PoC·지원·리뉴얼·구축을 독립 생성하고 각 aggregate의 작업·증거·승인·이력 경계와 허용 edge를 잠근다.

Phase 2

KV 리뉴얼 수직 순환

자연어 → proposal → 승인 → writer → result를 causationId로 연결하고 결과 신호를 다음 관찰에 되돌린다.

Phase 3

전체 그래프 projection

Customer Context와 My Work에서 고객별 서브그래프를 합성하되 원본 도메인 writer와 권한 경계를 유지한다.

Phase 4

경계가 있는 역할별 AI

AI는 caseRef의 bounded subgraph만 읽고, 경계를 넘는 작업은 version이 남는 감사 가능한 handoff로 처리한다.

Phase 5

검증된 자가개선과 위임

개선 후보를 평가·승인·shadow/canary·감시·rollback한 뒤 안정된 version과 T0 행동만 승격한다.

11 · Hostile review

비전을 지키려면
낙관을 통제해야 한다.

자유 생성이 프로세스를 무너뜨리지 않는가?

업무의 존재만 연다. 자격검증, 등록, 상업 승인, SLA clock, 납품 검수, 외부 발송은 유지한다. “생성”과 “위험한 약속”을 하나로 보지 않는다.

Customer Context가 하나의 복잡한 만능 화면이 되지 않는가?

고객 화면은 현재 상황·진행 업무·다음 행동·마감·최근 증거만 보여준다. 상세는 typed workspace로 이동한다. Pipeline과 My Work도 peer entry point로 남는다.

AI가 잘못된 고객·자산을 연결하면?

parse와 commit을 분리하고 multi-match·abstain을 제공한다. 원문·proposal revision·사람 확인·payload hash·result를 실패 폐쇄 방식으로 남긴다.

관계가 자유로워지면 데이터 품질이 무너지지 않는가?

money·SLA·권한을 결정하는 hard edge는 typed FK로 유지한다. soft attachment도 scope 검증·감사하며 사용자 정의 관계 종류는 v1에서 금지한다.

독립 프로젝트를 위해 가짜 딜을 만들 것인가?

기본 목표는 nullable opportunity 관계다. shadow opportunity는 단일 forecast quarantine 정책을 증명한 짧은 전환안일 뿐이다.

모든 Phase 공통 출시 조건

Gate Matrix

action마다 precondition·risk·approver·override를 기계가 읽게 한다.

Ownership

free-text 담당자가 아니라 assignment와 revision을 사용한다.

Dedup

자연키 후보·기존 건 연결·병합·AI abstain을 제공한다.

Metrics first

create source·duplicate·gate block·forecast error를 출시 전에 기록한다.

Fail-closed execution

label-only gate를 synchronous enforcement로 바꾸고 actor-aware tier를 적용한다.

AI principal

역할별 keyring·service principal·사람 sponsor·subjectId/jti를 남긴다.

Payload binding

승인 canonical hash와 실행 payload가 다르면 transaction을 중단한다.

Hardened audit

입력→제안→revision→hash→결과를 scoped chain에 원자적으로 기록한다.

Graph boundary

node/edge registry와 tenant scope를 강제하고 경계마다 권한·위험을 다시 계산한다.

Improvement gate

평가·사람 승인·version·canary·rollback pointer 없는 개선 후보는 production에 반영하지 않는다.
