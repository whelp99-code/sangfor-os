Reproduction under set -euo pipefail (isolated):

Explanation: when the target port has no listener, the [[ -n "$pid" ]] test
in the && chain evaluates false, so the whole compound command (and thus the
function/top-level call) returns exit status 1. Because scripts/dev-up.sh sets
'set -euo pipefail' at the top and calls kill_port as a bare top-level statement
(not inside an if/while condition), that nonzero status kills the entire script
immediately — before api or web is ever started. This is why dev-up.sh's own run
stopped right after '[dev-up] postgres ready' with exit code 1, and no
/tmp/sangfor-api.log or /tmp/sangfor-web.log were ever created.

Root cause 1 (as diagnosed): `[[ -n "$pid" ]] && { kill ...; log ...; }` as a bare
top-level statement under `set -euo pipefail` returns exit 1 when the port has no
listener (the `&&` short-circuits, and that nonzero status propagates out of the
function and kills the whole script). Fixed by converting to `if ... ; then ... fi`,
which preserves behavior (kill if pid found, silently pass otherwise) without ever
producing a nonzero exit status of its own.

grep -n '\[\[ -n' scripts/*.sh was run to check for the same accident pattern
elsewhere. scripts/dev-down.sh:9 had the identical shape (`[[ -n "$pid" ]] && {...}`
as a bare statement inside a `for` loop body, also under `set -euo pipefail`) — same
bug, would silently skip/abort mid-loop when either port had no listener. Fixed with
the same if/then/fi conversion. All other `[[ -n ... ]]` hits in scripts/*.sh
(backup-db.sh, check-apm-readiness.sh, check-mail-oauth.sh, ops-apm-test-event.sh,
restore-db.sh, run-all-checks.sh, route-smoke.sh, setup-github.sh) are already used
as `if`/pattern conditions or are otherwise not bare top-level && chains, so left
untouched (out of scope — no accident risk there for this run).

Root cause 2 (found only after fixing #1, since the script never previously reached
this line): scripts/dev-up.sh:45 had `log "starting api on :$API_PORT…"` — the
unbraced `$API_PORT` immediately followed by the U+2026 ellipsis character. Under
this shell's default locale (LANG=en_US.UTF-8) and `set -u`, bash's multibyte-aware
identifier scan glues the ellipsis's UTF-8 bytes onto the variable name, so it reads
the reference as the (unset) variable `API_PORT…` and aborts with "unbound variable"
under `set -u` — killing the script immediately after the postgres step, before api
or web ever started. Reproduced in isolation:
  $ API_PORT=3200 bash -uc 'echo "x:$API_PORT…y"'
  bash: API_PORT<0xe2><0x80><0xa6>: unbound variable
Fixed by bracing the expansion: `${API_PORT}…` (cosmetic-only change to a log
string; disambiguates the identifier boundary, no behavior change otherwise).
Confirmed no other unbraced-var-adjacent-to-non-ASCII occurrences remain in
scripts/dev-up.sh or scripts/dev-down.sh via

(no matches).
